# 配置分层架构

## 分层设计理念

OpenHarmony 的 Linux 内核配置采用五层分层架构，将不同职责的配置项组织在不同的配置文件中。这种设计借鉴了软件工程的模块化思想，通过清晰的职责划分实现配置项的有序管理和灵活扩展。五层配置分别是：基础通用配置（base_defconfig）、系统形态配置（type）、版本形态配置（form）、芯片平台配置（chip）和产品类型配置（product）。

分层架构的核心价值在于实现了配置项的**关注点分离**。底层配置关注系统级的通用需求，如 OpenHarmony 特性依赖的内核功能和安全红线特性；中间层配置关注系统形态和版本差异，如标准系统与小系统的不同调度策略；顶层配置关注具体硬件平台和产品形态，如特定芯片的驱动配置。这种分层使得不同角色的开发者可以专注于各自负责的配置层，减少配置冲突和维护复杂度。

分层架构还实现了配置项的**渐进式覆盖**机制。基础配置作为底层基础设施，具有不可覆盖性，确保所有平台都满足基本要求；上层配置可以覆盖下层配置，实现硬件差异化和产品定制化。这种机制既保证了系统的一致性，又提供了足够的灵活性。

## 配置层级详解

### 第一层：base_defconfig（基础通用配置）

基础通用配置层是整个配置体系的底座，包含 OpenHarmony 系统运行所必需的**内核必选模块**以及**安全红线特性**。这一层的配置具有最高优先级，任何情况下都不应被上层配置覆盖。

根据 README_zh.md 的描述，base_defconfig 中包含的配置项具有以下特点：首先，这些配置项是 OpenHarmony 特性所依赖的内核功能，关闭它们会导致系统无法正常运行；其次，这些配置项代表安全合规的底线要求，关闭它们会导致系统不满足基本的安全标准；最后，新增或调整这一层的配置需要经过内核-sig 例会的评审和批准，确保变更的合理性和影响范围的充分评估。

base_defconfig 的文件路径为 `linux-6.6/base_defconfig`（Linux 6.6 版本）。对于 Linux 4.19 和 5.10 版本，基础配置的功能分散在对应的 standard_common_defconfig 和 small_common_defconfig 中，这是由于历史原因导致的结构差异。

### 第二层：type（系统形态配置）

系统形态配置层区分了 OpenHarmony 的两种主要系统形态：标准系统（standard）和小系统（small）。这两种系统在资源占用、功能完整性和应用场景上有显著差异，需要通过不同的配置项来适应。

标准系统适用于功能丰富的智能设备，如智能手机、平板、智能电视等。标准系统的配置侧重于支持完整的服务框架、丰富的系统 API、多任务管理和图形界面能力。标准系统配置对应的文件是 `linux-5.10/type/standard_defconfig` 和 `linux-6.6/type/standard_defconfig`。

小系统适用于资源受限的物联网设备，如智能家居产品、传感器节点、可穿戴设备等。小系统的配置侧重于轻量级的系统服务、低内存占用、快速启动和基本的设备互联能力。小系统配置对应的文件是 `linux-5.10/type/small_defconfig` 和 `linux-6.6/type/small_defconfig`。

系统形态配置层通过 `build_type` 编译参数来确定加载哪个配置文件。构建系统根据该参数的值，读取对应的 type 配置文件并与 base 层配置合并。

### 第三层：form（版本形态配置）

版本形态配置层用于区分同一系统形态下的不同版本类型，如调试版本（debug）和发布版本（release）。这一层是可选配置层，如果对应的配置文件不存在，构建系统会忽略该层继续处理下一层。

调试版本配置通常包含额外的内核调试功能，如内核日志详细化、调试接口启用、错误检测增强等。这些功能有助于开发和调试阶段的问题定位，但会增加系统资源消耗，因此在发布版本中通常会被关闭或简化。

版本形态配置层通过 `build_variant` 编译参数来确定。由于本仓库目前没有提供 form 层的实际配置文件（README_zh.md 指出 `form/debug_defconfig` 目前无配置需求），这一层在当前版本中基本不发挥作用。

### 第四层：chip（芯片平台配置）

芯片平台配置层由具体的芯片厂商提供，包含与特定芯片和开发板相关的内核模块、驱动、硬件特性等配置。这一层是必选配置层，每个目标平台都必须提供对应的芯片配置。

芯片平台配置覆盖的内容通常包括：CPU 架构相关配置（如 ARM32 或 ARM64）、时钟频率和电源管理配置、外设驱动配置（如 GPIO、I2C、SPI、UART 等）、特定芯片的硬件加速器配置，以及设备树（Device Tree）相关的配置。

芯片平台配置层通过 `target_cpu` 编译参数来确定文件选择。例如，对于 Hi3516DV300 芯片，配置文件的路径模式为 `linux-5.10/arch/arm/configs/hi3516dv300_*_defconfig`；对于 RK3568 芯片，配置文件的路径模式为 `rk3568/arch/arm64_defconfig`。

### 第五层：product（产品类型配置）

产品类型配置层用于在同芯片平台的基础上区分不同的产品形态。例如，同一款芯片可能同时用于智能音箱和智能手表两种产品，这两种产品虽然硬件平台相同，但功能需求和资源分配可能有所差异，需要通过产品配置层来体现。

这一层是可选配置层，只有当同一芯片平台需要支持多种产品形态时才需要提供。产品配置通常包含：产品特定的功能开关、资源分配策略（如内存划分）、默认系统参数、安全策略定制等内容。

产品类型配置层通过 `device_type` 编译参数来确定。由于大多数开发板直接对应单一产品形态，这一层在当前仓库中几乎没有实际使用。

## 配置加载机制

### 加载顺序

OpenHarmony 的配置系统按照固定的顺序依次加载各层配置文件：base → type → form → chip → product。这个顺序是设计时确定的，体现了从通用到特殊、从稳定到灵活的配置管理理念。

加载顺序的设计遵循以下原则：稳定性优先，将最稳定、最不易变化的配置放在底层；优先级明确，后加载的配置可以覆盖先加载的配置；职责清晰，每层配置只关注特定领域的配置项。

### 合并规则

配置合并采用**后覆盖前**的规则，即后加载的配置文件中同名的配置项会覆盖先加载的同名配置项。这个规则简单直观，但在实际使用中需要注意以下情况。

对于布尔类型的配置项（y/n），后加载的配置会完全替换先加载的值。如果先加载配置中某项为 y，但后加载配置中该项不存在，则该项保持 y（不会被重置为 n）。这意味着上层配置如果要关闭某项功能，不能仅仅省略该配置项，而必须显式地设置为 n。

对于字符串类型的配置项（如路径、参数列表等），后加载的配置会完全替换先加载的值，不存在增量合并。这要求产品配置在需要定制字符串值时必须提供完整的值，而不能只提供增量部分。

### 构建参数映射

构建系统将编译参数映射到对应的配置文件路径。根据 README_zh.md 和 kernel.mk 的定义，主要的映射关系如下。

`build_type` 参数映射到 type 层的文件名：参数值为 `standard` 时读取 `standard_defconfig`，参数值为 `small` 时读取 `small_defconfig`。

`target_cpu` 参数映射到 chip 层的路径：参数值如 `hi3516dv300`、`rk3568` 等，对应 `linux-5.10/arch/arm/configs/${target_cpu}_${build_type}_defconfig` 或类似的路径模式。

`device_type` 参数映射到 product 层的路径：用于在同一芯片平台基础上区分不同产品。

`build_variant` 参数映射到 form 层的路径：参数值如 `debug`、`release` 等，对应不同版本类型的配置。

## 配置项分类

### 按功能领域分类

根据内核配置项的功能属性，可以将其划分为以下几个主要领域。

**处理器与架构配置**：包括 CPU 架构选择（ARM/ARM64）、内核子架构选项、处理器类型、指令集支持等。这部分配置决定了内核运行的硬件基础，通常在 chip 层确定。

**内存管理配置**：包括内存分配策略、页面大小、交换空间、内存压缩、透明大页等。内存管理配置对系统性能和稳定性有重要影响，需要根据目标平台的物理内存容量来调整。

**进程调度配置**：包括调度器选择（CFS、RT、Deadline 等）、任务优先级、CPU 亲和性、负载均衡等。标准系统和小系统可能采用不同的调度策略以适应不同的实时性需求。

**文件系统配置**：包括根文件系统类型、支持的文件系统、文件系统缓存、IO 调度器等。文件系统配置需要与实际使用的根文件系统类型匹配。

**网络配置**：包括网络协议栈支持（TCP/IP、IPv6 等）、网络接口驱动、网络安全（TLS、IPsec）等。网络功能在标准系统中通常是必需的，在小系统中可能是可选的。

**设备驱动配置**：包括字符设备、块设备、网络设备、USB 设备等各类驱动的支持。设备驱动配置主要在 chip 层确定，取决于目标平台的硬件配置。

**安全配置**：包括 SELinux/AppArmor、加密算法、安全启动、内核完整性保护等。安全配置中的红线特性必须在 base 层确保开启。

### 按必选程度分类

根据配置项的重要性和必选程度，可以将其划分为以下几类。

**必选配置**：这些配置项是 OpenHarmony 系统运行所必需的，关闭它们会导致系统无法启动或核心功能失效。必选配置主要集中在 base 层和 type 层。

**推荐配置**：这些配置项能提升系统性能和功能完整性，但关闭它们系统仍可运行。推荐配置主要根据产品需求和产品经理的决策来确定。

**可选配置**：这些配置项对应特定的功能或硬件支持，如特定的驱动、文件系统、网络协议等。可选配置主要根据实际需求在 chip 或 product 层决定是否开启。

**调试配置**：这些配置项仅用于开发和调试阶段，如内核调试接口、详细日志、错误检测增强等。调试配置通常在 form 层的 debug 版本中启用。

## 配置管理最佳实践

### 平台适配时的配置调整

在进行新平台适配时，建议按照以下步骤进行配置调整。

第一步是确认基础配置适用性，检查 base_defconfig 和对应的 type 配置是否满足新平台的基本需求。如果发现必选配置不兼容新平台的硬件，需要评估是修改平台设计还是推动基础配置的演进。

第二步是添加芯片平台配置，根据新平台的硬件规格创建 chip 层的配置文件。这包括 CPU 架构配置、外设驱动配置、时钟电源配置等。建议参考同类型已有平台的配置文件作为起点。

第三步是验证配置正确性，使用新平台的配置进行内核编译，检查是否有配置相关的编译错误或运行时问题。重点关注设备树配置与 defconfig 的一致性。

第四步是优化配置性能，根据实际测试结果调整配置参数，如 IO 调度器选择、内存管理参数、调度策略等，以获得最佳的系统性能和功耗表现。

### 配置版本管理

配置文件的版本管理需要与 OpenHarmony 版本同步。建议在每次 OpenHarmony 版本发布时同步更新本仓库的配置，并保持以下实践。

在变更记录方面，所有配置变更都应该有清晰的 commit message，说明变更的原因、影响范围和测试情况。避免无描述的 "update config" 或 "fix" 这样的提交信息。

在兼容性检查方面，新增配置项时需要评估对已有平台的影响，确保新配置不会意外破坏已有平台的构建。必要时可以在 commit 中添加配置兼容性说明。

在社区协作方面，重要的配置变更（如基础配置的修改）应该在对应的 SIG（Special Interest Group）会议中讨论和评审，特别是涉及安全相关的配置。
