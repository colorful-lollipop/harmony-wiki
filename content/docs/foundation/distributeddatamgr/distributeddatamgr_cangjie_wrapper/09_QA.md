# 常见问题 (FAQ)

## 文档目的

本文档收集开发 distributeddatamgr_cangjie_wrapper 过程中的常见问题和解决方案。

## 适用范围

本文档适用于：
- 使用仓颉语言进行应用开发的开发者
- 维护本项目的贡献者
- 集成此模块的系统工程师

## 构建相关问题

### Q1: 编译时报错 "Cannot find external module"

**问题描述**:
```
ERROR: Cannot find external module "preferences:cj_preferences_ffi"
```

**原因**:
底层 C++ 组件未正确安装或配置。

**解决方案**:
1. 确认已安装对应的底层组件（distributeddatamgr_preferences）
2. 检查 `--product-name` 参数是否包含必要的子系统
3. 运行 `hb build --list-components` 检查可用组件

**相关文档**: [06_GN_Targets.md](06_GN_Targets.md)

---

### Q2: Windows/Mac 平台编译失败

**问题描述**:
```
ERROR: No matching function for call to "FfiOHOSPreferencesGetPreferences"
```

**原因**:
Mock 实现未提供所有必需的 FFI 函数。

**解决方案**:
1. 检查 `mock/*.cj` 文件是否包含所有必需的函数声明
2. Mock 实现应返回合理的默认值或抛出适当的异常
3. 仅用于开发测试，生产环境使用真实实现

**相关文档**: [02_Directory_Structure.md](02_Directory_Structure.md#8-mock-测试桩模块)

---

### Q3: 产物大小超出限制

**问题描述**:
```
WARNING: libohos.data.distributed_kv_store.so size (850KB) exceeds limit (800KB)
```

**原因**:
代码膨胀导致 ROM 占用超标。

**解决方案**:
1. 优化 FFI 调用，减少不必要的字符串转换
2. 移除未使用的函数和类型
3. 考虑拆分大模块为多个子模块

**相关文档**: [01_Project_Boundaries.md](01_Project_Boundaries.md#资源占用)

## API 使用相关问题

### Q4: FFI 调用返回错误码 14800000

**问题描述**:
```cangjie
throw BusinessException(14800000, "Inner error.")
```

**原因**:
通用内部错误，可能是：
1. 底层 C++ 服务未响应
2. 参数验证失败
3. 资源不足

**解决方案**:
1. 检查 HiLog 日志获取详细错误信息
2. 确认传入参数类型和值是否正确
3. 验证 StageContext 或 BaseContext 是否有效

**相关文档**: [04_Public_API.md](04_Public_API.md) (错误码部分)

---

### Q5: executeSql 执行失败，权限错误

**问题描述**:
```cangjie
rdbStore.executeSql("DROP TABLE sensitive_data;")
// 错误: 权限拒绝 (14800023)
```

**原因**:
执行可能危险的 SQL 操作（如 DROP, ALTER），被底层 SQLite 拒绝。

**解决方案**:
1. 仅执行安全的 SQL 操作（CREATE TABLE, DELETE TABLE）
2. 使用 querySql 替代 executeSql 进行数据操作
3. 检查数据库文件的权限设置

**相关文档**: [08_Security_Review.md](08_Security_Review.md#1-sql-注入漏洞高危)

---

### Q6: KV Store 超时

**问题描述**:
```cangjie
kvStore.put("key", "value")
// 长时间无响应或超时错误
```

**原因**:
1. 数据库文件过大或损坏
2. 磁盘 I/O 瓶颈
3. 分布式同步网络延迟

**解决方案**:
1. 检查数据库文件大小，考虑清理旧数据
2. 使用批量操作（putBatch）而非单条 put
3. 检查网络连接和同步配置
4. 增加超时时间配置（如支持）

**相关文档**: [04_Public_API.md](04_Public_API.md#1-分布式键值数据库distributedkvstore)

---

### Q7: Preferences 持久化失败

**问题描述**:
```cangjie
preferences.put("setting", "value")
preferences.flush()
// 文件未更新或数据丢失
```

**原因**:
1. flush() 未被调用或调用失败
2. 存储类型配置错误（Xml vs Gskv）
3. 磁盘空间不足

**解决方案**:
1. 确保在每次修改后调用 flush()
2. 检查返回值，处理异常
3. 验证 PreferencesOptions 配置是否正确
4. 检查应用是否有足够的磁盘空间权限

**相关文档**: [04_Public_API.md](04_Public_API.md#3-用户首选项preferences)

## 运行时问题

### Q8: 应用崩溃，内存访问错误

**问题描述**:
```
FATAL: segmentation fault (core dumped)
```

**原因**:
可能是 FFI 层的空指针解引用或内存错误。

**解决方案**:
1. 使用地址清理器（Address Sanitizer）重新编译
2. 检查所有 FFI 调用的参数是否非空
3. 确认 @C struct 的 free() 方法在所有代码路径中被调用
4. 添加单元测试覆盖边界情况

**相关文档**: [08_Security_Review.md](08_Security_Review.md#3-空指针解引用漏洞中危)

---

### Q9: 数据丢失或损坏

**问题描述**:
应用重启后，数据与之前不一致。

**原因**:
1. 未调用 flush() 或 close()
2. 崩溃导致数据未持久化
3. 并发写入导致竞争条件

**解决方案**:
1. 确保所有修改操作后调用 flush() (Preferences)
2. 使用事务（KV Store 支持事务）保护关键操作
3. 在应用生命周期结束时显式关闭数据库连接
4. 使用数据备份功能定期备份数据

**相关文档**: [04_Public_API.md](04_Public_API.md) (各模块的数据持久化说明)

## 安全相关问题

### Q10: 如何确保数据加密？

**问题描述**:
需要确保敏感数据在存储时被加密。

**解决方案**:
1. 设置 appropriate Security Level（S3 或 S4）
2. 提供 CryptoParam 配置（RDB）
3. 确保 KVOptions 的 encrypt 参数为 true
4. 妥善管理加密密钥（不要硬编码或记录到日志）

**相关文档**: [08_Security_Review.md](08_Security_Review.md#5-密钥泄露漏洞中危)

---

### Q11: 如何防止 SQL 注入？

**问题描述**:
使用 executeSql 时担心 SQL 注入攻击。

**解决方案**:
1. 优先使用 querySql (参数化查询) 而非 executeSql
2. 如必须使用 executeSql，在应用层进行严格的输入验证
3. 避免拼接用户输入到 SQL 字符串
4. 使用白名单验证表名和列名

**相关文档**: [08_Security_Review.md](08_Security_Review.md#1-sql-注入漏洞高危)

---

### Q12: 如何验证权限？

**问题描述**:
如何确保只有授权应用能访问数据。

**解决方案**:
1. 在应用清单中声明所需的权限
2. 运行时检查权限授予状态
3. 使用 Bundle Name 验证防止应用冒用其他应用数据
4. 定期审计数据访问日志

**注意**: 当前 Wrapper 层未提供权限验证 API，需在应用层实现。

**相关文档**: [08_Security_Review.md](08_Security_Review.md#3-权限绕过漏洞高危)

## 开发调试相关问题

### Q13: 如何启用详细日志？

**问题描述**:
需要查看详细的 FFI 调用日志以调试问题。

**解决方案**:
1. 修改 `hilog` 配置启用 DEBUG 级别
2. 检查各模块的 LOG 宏使用（如 `PREFERENCES_LOG.error()`）
3. 在测试中设置环境变量启用详细日志
4. 使用 `hdc shell hilog -R` 命令实时查看日志

**相关文档**: [02_Directory_Structure.md](02_Directory_Structure.md) (日志使用说明)

---

### Q14: Mock 模式下如何测试真实功能？

**问题描述**:
在 Windows/Mac 开发，需要测试真实功能。

**解决方案**:
1. 使用远程设备进行测试（需要 OpenHarmony 设备）
2. 使用模拟器（如果有 OpenHarmony 模拟器）
3. 仅在 Mock 模式下进行 UI 和逻辑测试
4. 使用 CI/CD 在真实设备上运行测试

**注意**: Mock 实现仅用于开发环境，生产环境必须使用真实实现。

**相关文档**: [02_Directory_Structure.md](02_Directory_Structure.md#8-mock-测试桩模块)

## 性能相关问题

### Q15: 数据库查询性能差

**问题描述**:
查询操作响应时间过长。

**原因**:
1. 缺少合适的索引
2. 查询条件未优化
3. 单次返回数据量过大

**解决方案**:
1. 为常用查询字段创建索引
2. 使用 limit() 分页返回结果
3. 优化查询条件，避免全表扫描
4. 考虑使用分布式查询减少数据传输量
5. 定期清理过期数据减少数据库大小

**相关文档**: [04_Public_API.md](04_Public_API.md) (Query 和 Predicates 使用)

---

### Q16: 批量操作仍然很慢

**问题描述**:
使用 putBatch 批量插入，性能提升不明显。

**原因**:
1. 单次批量数据量仍然过大
2. 数据库锁竞争
3. 底层同步机制延迟

**解决方案**:
1. 控制单次批量大小（建议 < 100 条）
2. 考虑异步提交（如果支持）
3. 在低峰期执行批量操作
4. 监控底层 C++ 服务的性能

**相关文档**: [04_Public_API.md](04_Public_API.md) (批量操作 API)

### Q17: 如何获取更多错误信息？

**问题描述**:
通用错误代码未提供足够的信息。

**解决方案**:
1. 查看 HiLog 日志中的详细错误消息

3. 在测试代码中捕获 FFI 返回的错误码
4. 联系底层组件维护者获取详细文档

**相关文档**: [04_Public_API.md](04_Public_API.md) (错误码映射)

### Q18: 如何报告 Bug？

**问题描述**:
发现代码问题或文档错误。

**解决方案**:
1. 在 [OpenHarmony Gitee](https://gitee.com/openharmony) 提交 Issue
2. 提供详细的复现步骤和环境信息
3. 包含相关的日志和错误信息
4. 说明预期的行为和实际行为的差异

**注意**: 提交 Issue 前请先搜索现有 Issue 避免重复。
