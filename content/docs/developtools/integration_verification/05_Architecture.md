# 架构设计

## 概述

集成验证部件采用模块化的架构设计，将测试框架、工具集和用例管理有机结合。其核心架构围绕门禁冒烟和每日构建两大功能展开，为 OpenHarmony 系统的质量保障提供完整支持。

## 核心模块

### 门禁冒烟模块

**模块路径**：`cases/smoke/`

**职责**：提供门禁级别的快速测试能力，在代码提交时执行。

#### 功能特性

| 特性 | 说明 |
|------|------|
| 基本功能测试 | 验证系统核心功能的基本可用性 |
| 部件功能测试 | 针对各子系统的功能进行验证 |
| 端到端场景测试 | 按照实际业务场景进行完整流程测试 |

**证据来源**：`README.md:4-5`

### 每日构建模块

**模块路径**：`cases/daily/`

**职责**：提供每日级别的全面测试能力，定期执行全面验证。

#### 功能特性

| 特性 | 说明 |
|------|------|
| 版本归档 | 保存每日构建的版本快照 |
| 全量 TDD 测试 | 执行完整的测试用例集 |
| 最小系统测试 | 验证最小配置下的系统功能 |
| 架构看护检查 | 确保系统架构的合规性 |

**证据来源**：`README.md:6-7`

## 用例配置机制

### repo_cases_matrix.csv 配置模型

用例与仓库、开发板的关联关系通过矩阵形式配置。

**证据来源**：`README.md:35-41`

```
仓库 ─────────────────────────────────────────────────────────────▶ 开发板

        │   board1      board2      board3      ...
────────┼────────────────────────────────────────────────────────
repo1   │ test1        test1;test2  test3
repo2   │ test1;test2  test1        -
repo3   │ -            test1;test3  test1;test2
```

### 配置规则

1. **行维度**：每个仓库一行
2. **列维度**：各开发板一列
3. **单元格值**：针对该仓库+开发板组合的用例名称（分号分隔）
4. **特殊值**：`-` 表示该组合不执行测试

## 工具集成架构

### 工具分类

集成验证部件提供多种支撑工具，按功能分类如下：

| 类别 | 工具 | 职责 |
|------|------|------|
| 资源分析 | rom_ram_analyzer | ROM/RAM 占用分析 |
| 自动化 | fotff | OTA 测试框架 |
| 合规检查 | opensource_tools | 开源许可证检查 |
| 代码质量 | code_access_control | 代码访问控制 |
| 依赖管理 | deps_guard | 依赖关系守护 |

## 扩展性设计

### 用例扩展

新增测试用例只需：
1. 在对应目录下创建用例文件
2. 在 `repo_cases_matrix.csv` 中配置关联关系
3. 遵循现有的用例命名规范

### 工具扩展

新增工具只需：
1. 在 `tools/` 目录下创建工具目录
2. 实现标准化的命令行接口
3. 在 `check.py` 中注册集成

## 架构特点

### 模块解耦

- 测试用例与测试框架分离
- 工具与业务流程分离
- 配置与代码分离

### 灵活配置

- 用例与仓库/开发板通过 CSV 配置关联
- 支持多种开发板类型
- 支持用例分组和选择

### 可扩展性

- 易于新增测试类型
- 易于集成新工具
- 易于适配新设备
